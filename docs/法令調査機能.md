# 法令調査機能（法令 RAG）

法令に関する質問を自然言語で入力すると、関連する法令・条文を検索し、出典（参照条文）付きの
Markdown レポートを生成する機能。サイドメニュー「法令調査」／トップのカードから利用する。

## 表出・導線

- ルート：`/law-rag`（`packages/web/src/features/law-rag/`）
- メニュー／ランディングカード／ルートはいずれも `isUseCaseEnabled('rag')` で表出を制御する。
- 機能 ON/OFF は **embedding profile（`rag`）連動**。profile を ON にすると自動でメニューに現れ、
  OFF のときは導線ごと非表示になる（「メニュー非表示なのに経路だけ生きて壊れる」を防ぐ既存方針に整合）。

## バックエンド契約

- `POST /api/law-rag/query`（api 側 `src/routes/lawRag/`）。
  - リクエスト：`{ inputs: { question: string } }`
  - レスポンス：`{ outputs: <出典結合済み Markdown レポート>, usageMetadata: [] }`
- 法令名推定 → 法令特定 → 条文選別 → レポート生成 → 出典結合の、法令専用パイプライン。
- 一般文書 RAG（`/api/rag/query`）とは経路が別。出典はレポート本文に結合済みのため、画面は
  `outputs` を Markdown としてそのまま描画する（追加の出典 UI は持たない）。
- レポート生成は法令全文を扱うためレイテンシが大きい（数十秒程度）。フロントはタイムアウトを設けず、
  nginx `/api/` の長尺許容（Code Interpreter と共用）に委ねる。

## 設計判断（重要・将来の改修判断のために残す）

本機能は **チャットに統合せず、独立した専用ページ**として実装した。理由は以下のとおり。

1. **本プロジェクトのコンセプト＝「貧弱な PC でも最小構成で起動して実験する」**。
   法令 RAG は embedding スタック（埋め込み生成＋法令 DB）に依存する重めの機能であり、
   embedding profile（`rag`）を ON にしたときだけ使える「実験用の独立メニュー」として切り出すのが、
   最小構成・段階的有効化の思想に最も素直に合う。チャットへ常時混ぜ込むと、profile 構成と UI の
   対応関係が分かりにくくなり、最小構成で動かす利用者の体験を損なう。
2. **法令専用パイプラインは汎用 chat / 汎用 RAG と経路・出力契約が別**（推定→特定→選別→レポート→出典結合）。
   独立ページにすることで、想定用途・留意点・出典の扱いをその機能の文脈で明示でき、責務が分離される。
3. **profile 連動キーは専用キー（`lawRag`）を新設せず `rag` を再利用**した。法令 RAG の実依存は
   汎用 RAG と同じ embedding スタックであり、api 側ゲートも `requireUseCase('rag')` で一致している。
   専用キーを足すと compose／nginx（config.js 注入）／api ゲートの 3 箇所を増やすことになり、
   「最小構成」コンセプトに反する。実依存に忠実な `rag` 連動が最小かつ正確。

> もし将来「チャットに法令調査モードを統合してほしい」という要望が出た場合は、上記 1〜3 の
> トレードオフ（最小構成・責務分離・profile 連動の単純さ）を踏まえて再検討すること。
> 独立ページは設計上の意図的な選択であり、実装の手抜きではない。

## 使用モデルとハードウェア要件（重要）

法令調査フォームには **使用 LLM の選択** がある（チャットと同じ `MODEL_IDS` 由来の一覧・選択は
`useSelectedModel` で永続化）。法令調査は「法令名推定 → 条文選別 → 出典付きレポート生成」の
**3 回の逐次 LLM 呼び出し**を、法令本文という大きなコンテキスト上で行うため、本アプリ群の中で
**最も計算負荷が高い機能**である。モデル選択は、この負荷に対するユーザー側のトレードオフ調整手段。

- **高性能モデル（例 gemma 系）**：出典・条文引用の精度は高いが、CPU のみの環境では 1 クエリに
  数分〜十数分かかり、タイムアウトすることがある。
- **小型モデル（例 llama3.2:3b）**：応答は速いが、法令名の取り違え・出典欠落など**精度が大きく低下**
  し得る（法律質問では誤情報になり得るため、出典条文の原典確認が必須）。

> **ハードウェア指針**：実測では、CPU のみ・16GB クラスの環境では「速い小型モデル＝低品質」/
> 「高品質な高性能モデル＝タイムアウト」となり、両立が難しい。**出典付きの実用品質を妥当な応答時間で
> 得るには、GPU か十分な計算資源を推奨**する。これは法令調査が最難関機能であることに起因する
> 設計上の前提であり、他機能（チャット・翻訳・データ分析等）は貧弱 PC でも実用範囲で動く。

## 留意点

- 生成レポートはローカル小型 LLM と法令データベースに基づく**参考情報**であり、法的助言ではない。
- 法令データの取り込み時点以降の改正は反映されない場合がある。重要な判断の前には出典条文の原典
  （e-Gov 法令検索等）を確認すること。
- 法令データの投入手順は配布リポジトリ（genai-deploy-onpre）の `docs/law-rag-setup.md` を参照。
